# External review evidence checklist

Use one copy of this checklist for each independent reviewer. The first review round should include at least two reviewers; the project roadmap retains a target of at least three before 1.0.

## Before the review

- [ ] Reviewer is suitably independent.
- [ ] Reviewer role and relevant experience are recorded.
- [ ] TriageBloom version is recorded.
- [ ] Exact commit SHA is recorded.
- [ ] Review date is recorded.
- [ ] Test mode is recorded: CLI / local Streamlit / public demo.
- [ ] Only synthetic, public-licensed, or explicitly authorised sanitised data will be used.
- [ ] Reviewer received the public README and independent review guide.
- [ ] Reviewer was not given pre-written praise or suggested scores.

## During the review

- [ ] Installation/opening outcome recorded.
- [ ] Combined incident scenario tested.
- [ ] At least one authentication finding inspected.
- [ ] At least one process or correlation finding inspected.
- [ ] At least one benign synthetic case tested.
- [ ] At least one malicious synthetic case tested.
- [ ] Evidence IDs checked.
- [ ] ATT&CK mapping reviewed.
- [ ] Investigation guidance reviewed.
- [ ] Pseudonymised report reviewed.
- [ ] Any false positive recorded.
- [ ] Any false negative recorded.
- [ ] Any privacy/security concern recorded.
- [ ] Any usability problem recorded.
- [ ] Reviewer compared TriageBloom with tools/workflows they already know.

## After the review

- [ ] Original completed feedback form preserved privately.
- [ ] Email/message showing the source of the feedback preserved.
- [ ] Reviewer credentials or public professional profile retained.
- [ ] Permission to quote is recorded.
- [ ] Negative feedback remains in the raw record.
- [ ] Public summary, if any, distinguishes reviewer opinion from measured results.
- [ ] No claim of organisational adoption is made unless the organisation actually approved or used the tool.
- [ ] Any issue opened from feedback links back to the affected version/commit.
- [ ] Any code change caused by the review is traceable through a commit or pull request.

## Stronger evidence if it genuinely occurs

- [ ] Reviewer opens a substantive GitHub issue.
- [ ] Reviewer contributes a pull request.
- [ ] Reviewer uses TriageBloom independently after the review.
- [ ] Reviewer references the tool in a talk, article, course, report, or publication.
- [ ] An organisation runs an authorised pilot.
- [ ] A second independent party reproduces a benchmark/evaluation result.

Do not create or solicit artificial stars, forks, issues, testimonials, downloads, or endorsements for evidence purposes.
